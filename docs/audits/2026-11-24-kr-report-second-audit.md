## B. 기술·아키텍처 우선순위 5건

### 1. 오래된 집계로 최신 요약이 덮임 · 높음 · 수정

- **영향과 재현**. 임시 SQLite의 첫 집계가 리포트 1건을 읽은 직후 멈추게 했다. 다른 연결에서 두 번째 리포트를 쓰고 새 집계가 2건을 저장한 뒤 이전 집계를 재개했다. 원문은 2건인데 최종 집계는 1건이었다. 예약·수동 poll은 공통 집계 경로를 호출하므로 겹침 시 브리핑·웹의 집계값이 과소 표시될 수 있다.
- **원인과 조치**. 원문 조회는 별도 연결에서 먼저 끝났고 일자 행 교체는 이후 트랜잭션에서 실행됐다. 조회 SQL과 정렬을 공유하고 같은 연결에서 `BEGIN IMMEDIATE` 후 원문 조회, 집계, 행 교체를 수행한다. 실패하면 트랜잭션이 롤백된다.
- **회귀 위험과 검증**. 쓰기 잠금이 집계 계산 동안 유지된다. 많은 리포트가 저장된 날의 쓰기 대기는 운영 부하에서 미측정이다. 임시 DB 테스트는 계산을 정지한 채 다른 작성자의 잠금 시도가 실패하는지 확인하고 SQL trace로 원문 조회보다 트랜잭션 시작이 앞섰음을 검사한다. 기존 코드에서 실패했고 수정 후 통과했다.
- **위치**. [저장소 집계](../../src/stock_monitor/db/repository.py#L762) · [경합 회귀](../../tests/test_repository.py#L89)

### 2. compact 일일 DTO와 화면 검증기 불일치 · 높음 · 수정

- **영향과 재현**. 10월 8일 리포트 14건을 저장하고 Toss 값과 저장 뉴스를 비워 둔다. `GET /api/daily/2026-10-08`은 200과 정상 건수를 반환한다. 수정 전 `/daily/2026-10-08`은 형식 오류를 표시했고 Main과 V2는 해당 데이터를 표시하지 못했다.
- **원인과 조치**. 일일 API는 Python과 동일하게 객체의 `null`을 재귀적으로 생략하지만 화면 검증기는 저장 시장 날짜, 수급·뉴스 시각과 일부 하위 필드에서 명시적 `null`을 요구했다. compact 응답에서 생략 가능한 필드만 타입과 검사에 반영했다. 선택일보다 미래인 값과 완료 상태가 일치하지 않는 응답은 거부한다.
- **회귀 위험과 검증**. 필수 화면 데이터의 검사가 느슨해지면 날짜·출처 경계가 약해질 수 있다. 오래된 검증 규칙 중 날짜·상태·숫자 타입을 보존했고 정상 compact 응답, 거짓 가용 상태, 미래 시장 날짜를 테스트했다. Python·Next DTO 동등성도 계속 확인했다.
- **위치**. [공개 DTO 생성](../../web/src/server/daily-snapshot.ts#L33) · [화면 검증기](../../web/src/domain/daily.ts#L382) · [액세스 경로 회귀](../../web/test/daily-snapshot.test.mjs#L93)

### 3. Telegram 명령 커서 경합 · 중간 · 수정

- **영향과 재현**. 같은 임시 JSON 상태로 두 명령 처리 호출을 겹치고, 모의 Telegram API에서 양쪽에 같은 `/help` 업데이트를 반환했다. 수정 전 모의 전송이 2회 기록됐다. 예약 워커와 수동 단발 명령이 겹치면 응답이나 명령 효과가 중복될 수 있다.
- **원인과 조치**. 이전 발송 보호는 요약·장중·시장 브리핑 경로에 있었지만 명령 커서를 읽고 작업한 후 저장하는 흐름에는 직렬화가 없었다. 실제 상태 파일 옆의 기존 OS 잠금 방식을 재사용한다. 잠금 소유자가 있으면 다른 호출은 즉시 건너뛰고, 작업 본문에서 난 `BlockingIOError`는 호출자에게 전달한다.
- **회귀 위험과 검증**. 잠긴 동안 수동 단발 호출은 처리를 건너뛴다. 충돌한 업데이트는 소유자가 처리하거나 다음 주기에 다시 읽는다. 응답 후 커서 저장 전에 프로세스가 중단되는 별도 구간에는 이번 잠금이 전달 보장을 추가하지 않는다. 모의 전송 1회와 작업 중 오류 전파를 별도로 검증했다.
- **위치**. [명령 처리 입구](../../src/stock_monitor/cli.py#L43327) · [경합 및 오류 전파 회귀](../../tests/test_telegram_command_replay.py#L15)

### 4. 종목 코드 없는 과거 행 하나가 종목 탭 전체를 무효화 · 중간 · 수정

- **영향과 재현**. 선택일 DB에 코드가 있는 요약과 코드가 `NULL`인 과거 요약을 함께 넣는다. compact 응답에는 과거 행의 `stock_code`가 빠진다. 기존 탭 조합기가 바깥 DTO를 복사하면 엄격한 종목 탭 검증기가 이 행 때문에 전체 스냅샷을 거부한다.
- **원인과 조치**. 조합기가 가격·거래량 `null`은 복구하고 종목 코드는 놓쳤다. 탭 내부에서만 `stock_code: null`을 복구했고 공개 일일 JSON은 기존처럼 필드를 생략한다. 종목 코드가 없으면 상세 링크도 생성되지 않는다.
- **회귀 위험과 검증**. 인식 가능한 이전 행과 6자리 코드의 상세 이동 정책이 달라지면 안 된다. 회귀는 동일 DB에서 compact API와 엄격한 종목 탭 스냅샷 두 계약, Python 값 비교와 읽기 전용 파일 사용을 확인한다.
- **위치**. [탭 스냅샷 조합기](../../web/src/server/daily-tab-workspace.ts#L46) · [워크스페이스 회귀](../../web/test/daily-tab-workspace.test.mjs#L150)

### 5. 초기 응답에 비활성 탭까지 실림 · 낮음 · 측정 및 후속 검토

- **영향과 재현**. 같은 synthetic DB의 Main HTML에 `hidden`이 붙은 관찰·종목 패널의 콘텐츠가 둘 다 실렸다. 수정 전 루트 HTML 69,123 bytes, 날짜 지정 메인·관찰·종목 HTML이 각 70,651 / 70,663 / 70,655 bytes였다. 검증된 작은 화면에서도 탭 전환 전 데이터를 함께 전송한다.
- **원인과 제안**. 서버가 모든 패널을 생성하고 클라이언트가 활성 탭만 표시한다. 이렇게 하면 탭 전환은 빠르다. 저사양·모바일에서 HTML/RSC 크기와 첫 화면 지연을 먼저 측정한 후, 임계값을 넘는 경우 비활성 탭의 데이터 지연 로드를 비교한다.
- **회귀 위험**. 즉시 탭 전환, 뒤로 가기, 링크 직접 접근, 선택 종목과 쿼리 유지, 한 SQLite 스냅샷에서 일관된 후보를 표시하는 계약에 영향을 줄 수 있어 변경을 보류했다. 운영 병목 여부는 더 큰 데이터와 실제 단말 측정이 필요하다.
- **위치**. [서버 패널 조합](../../web/src/components/server/daily-tab-page.tsx#L28) · [클라이언트 표시](../../web/src/components/client/daily-tabs.tsx#L41)

추적 파일 변경은 총 17개다. 신규 감사 파일은 합성 데이터로 작성한 서로 다른 화면과 상태 증거로 검토했다. 이미지 33장은 정상 디코딩됐고 해시 중복이 없었다. 변경 텍스트와 감사 문서·JSON에서 토큰과 개인 키 패턴은 발견되지 않았다. 임시 DB, 로그, 테스트 실행기, 캐시, 빌드 출력, 설치 의존성, 환경 파일은 통합 목록에서 제외했다. 스테이징은 비어 있다.

**통합 판정은 준비 완료.** 확인한 원격 main과 기준점이 같고, 공통 상태 쓰기 잠금과 Toss 문구 수정의 회귀 검증이 통과했다. 이 판정은 개발 통합에 대한 것이다. 운영 배포는 아래 점검을 별도 승인 후 완료해야 한다.

### 운영 배포 전 필수 점검표

- [ ] **운영 기준 확인.** 운영 리비전과 배포 대상 SHA, 실제 SQLite DB·Telegram 상태 JSON 경로, DB 스키마, 예약 작업 실행 계정의 Python·Node·PATH를 기록한다. 배포 대상은 스키마 13을 지원한다. 스키마가 확인되지 않거나 지원 범위를 벗어나면 배포를 보류한다.
- [ ] **백업 및 복원 리허설.** 운영 DB는 SQLite 백업으로 만들고, 전환 시점에 Telegram 상태 JSON과 이전 실행 릴리스를 함께 보존한다. 승인된 격리 복제본에서 복원, 무결성·외래 키, 발송 이력·커서 확인까지 통과시킨다. DB와 JSON은 외부 발송을 포함한 하나의 트랜잭션으로 저장되지 않으므로 백업 시각과 복구 대상으로 삼을 커서를 기록한다.
- [ ] **스키마 12 → 13 판단.** 운영이 13이면 이 변경을 위해 스키마를 올릴 필요가 없다. 12라면 복제본에서 `db-migration-rehearsal`로 먼저 검증한다. 승인된 전환 시간에만 마이그레이션을 실행하고, 작성 프로세스를 재개하기 전에 스키마 13·무결성·외래 키를 확인한다. [마이그레이션 절차](../codex/mini-pc-runbook.md#schema-13-migration-backup-and-rollback)
- [ ] **기존 작성 프로세스 중지.** 전환 시간과 권한을 확정한다. 진행 중 발송의 종료를 확인하고 예약·수동 수집, 발송, Telegram 명령 워커의 이전 릴리스를 모두 멈춘 뒤 교체한다. 구·신 버전이 같은 DB나 상태 파일에 함께 쓰면 배포를 보류한다.
- [ ] **전환 후 검증.** DB 검증, 공개 `/health`·아카이브·선택일 요약, 문구와 기준일을 확인한다. 발송 이력의 `sending`·`ambiguous`는 자동 재발송 전에 운영자가 확인한다. 승인된 다음 정상 운영 주기에 집계 생성, 기존 발송 중복 여부, 명령 커서와 페이지 이동을 관찰한다.
- [ ] **롤백 조건과 보존.** 마이그레이션·무결성 검사 또는 핵심 경로가 실패하거나 반복 잠금 오류·중복 발송·커서 역행이 발생하면 재개를 중단한다. 실패 시점의 DB·필요한 SQLite sidecar·상태 JSON·로그를 먼저 보존한다. 스키마와 호환되는 이전 릴리스 및 검증된 백업을 사용한다. 복원 이후 재개 전에 백업 이후 쓰기와 발송 결과를 대조한다. [롤백 절차](../codex/mini-pc-runbook.md#schema-13-migration-backup-and-rollback)

### 허용 가능한 제한과 별도 후속 과제

- **이번 배포의 알려진 제한.** `/next`는 마지막으로 저장된 페이지를 사용한다. Telegram이 새 알림을 수락한 직후 페이지 상태가 저장되기 전에는 이전 페이지가 나올 수 있다. 실제 잠금 대기 시간의 상한은 미측정이다. Telegram이 답변을 수락한 뒤 커서 저장 전에 프로세스가 종료되면 답변이 재실행될 수 있다. 이전 백업을 복원하면 당시 커서로 돌아간다.
- **후속 과제 · 2027년 KRX 거래일.** 공식 연간 일정과 임시 휴장 근거를 확인하고 2027년 영업일·휴장일 및 연도 경계의 예약 실행 차단을 검증한다. 완료 기준은 2027년 자동 실행을 시작하기 전에 일정의 적용 범위와 회귀 테스트를 확인하는 것이다. [현재 달력](../../src/stock_monitor/config.py#L58)
- **후속 과제 · 장기 Telegram 중단 후 커서 복구.** 기존 `offset`이 재시작에 어떻게 사용되는지, 일주일 이상 새 업데이트가 없을 때의 ID 변경 및 이전 상태 복원 시 중복·누락 가능성을 격리된 검증 환경에서 확인한다. 완료 기준은 보류·재개 조건과 운영자 확인 절차를 문서화하고 커서 복구 회귀를 통과하는 것이다. [Telegram Update](https://core.telegram.org/bots/api#update) · [getUpdates](https://core.telegram.org/bots/api#getupdates)
